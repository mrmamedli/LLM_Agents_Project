## Продукт
Веб-приложение со вкладками предметов. В предмет загружают PDF (в MVP
только текстовые PDF). Агент на основе LLM:
  1. определяет тип документа (lecture | assignment | rules | other);
  2. пишет конспект (5-10 пунктов + ключевые термины);
  3. извлекает дедлайны и требования к домашкам, у каждого указана страница
     и цитата-источник;
  4. для заданий находит нужные лекции из этого же предмета.
Дедлайны собираются в календарь и экспортируются в .ics.
Принцип борьбы с галлюцинациями: если даты в документе нет, due_date = null,
дату не выдумывать.

## Стек и правила
- Python 3.12, FastAPI, SQLite (стандартный sqlite3, без ORM), pydantic v2,
  pypdf, icalendar, openai (SDK), python-dotenv, pytest.
- Фронтенд: ванильный HTML/JS без сборки, раздаётся FastAPI из app/static/.
- LLM: любой OpenAI-совместимый API. Переменные окружения: API_KEY,
  BASE_URL, MODEL_NAME, DATA_DIR (по умолчанию ./data). Ключи в коде
  не хардкодить.
- Запуск: `docker compose up`, приложение на порту 8000.
- Код чистый: type hints, короткие функции, докстринги только там, где они
  нужны. Никакого мёртвого кода, закомментированных кусков и TODO-мусора.
- Все зависимости запинены (package==x.y.z).
- Язык интерфейса: русский. Идентификаторы и комментарии в коде: английский.

### REST API (префикс /api)
GET  /api/subjects ; POST /api/subjects {name} ; DELETE /api/subjects/{id}
GET  /api/subjects/{id}/files

     создаёт запись со status=uploaded и запускает BackgroundTasks ->
     agent.processor.process_file(file_id); возвращает FileOut

Фронтенд опрашивает GET /api/files/{id}, пока status не станет done или error.

### Агент (app/agent)
Точка входа для бэкенда: `process_file(file_id: int) -> None`
(app/agent/processor.py). Она ставит status=processing, запускает агента,
в конце ставит done или error (с текстом ошибки) и никогда не бросает
исключения наружу.
Агентный цикл пишем сами, без LangChain, как на лекции 04:
  - декоратор @tool строит JSON-схему из сигнатуры и докстринга;
  - run(task, tools, system) -> str: цикл "вызов модели -> выполнение
    tool_calls -> результат обратно -> до ответа без tool_calls";
  - ограничение на число итераций (max 8) против зацикливания.
Инструменты агента (app/agent/tools.py):
  read_pdf(file_id, start_page, end_page) -> str
  list_materials(subject_id) -> str  (список файлов предмета: id, имя, тип,
                                      первая строка конспекта)
  save_summary(file_id, text, key_terms_json) -> str
  save_deadline(file_id, deadline_json) -> str  (валидируется по DeadlineExtraction)
  link_materials(deadline_id, file_ids_json) -> str
  set_doc_type(file_id, doc_type) -> str
Логика: длинные файлы читаются постранично кусками, конспект и дедлайны
получаются в структурированном виде (response_format json_schema на
FileAnalysis или аргументы tool с валидацией). Невалидный JSON даёт ровно
одну повторную попытку с текстом ошибки валидации. В системный промпт
всегда передаются текущая дата и часовой пояс Europe/Moscow, чтобы
разрешать относительные даты ("в пятницу"). Если дата относительная и
неоднозначная, то status=needs_confirmation и date_note хранит исходную
фразу. Если даты нет вообще, то due_date=null и status=undefined.

Идея: StudyHub, агент-ассистент для учебных материалов
1. Проблема
У студента на каждом предмете десяток файлов: лекции, описания проектов, условия домашек. Дедлайны и требования лежат в разных местах: в PDF, в чате группы, в середине слайда. В итоге:
непонятно, что сдавать и к какому сроку;
непонятно, какие материалы нужны для конкретной домашки;
перед контрольной нужно заново пролистывать 40 слайдов.
Наш собственный пример: в описании проекта написано «даты объявляются в чате», формула оценки лежит в одном абзаце, требования к репозиторию в другом, а чек-лист в третьем. Такой документ нельзя разобрать регулярками, его надо понимать.
2. Почему здесь нужен LLM (это те самые 4 «блокирующих» балла)
Материалы неструктурированные и разнородные. Это слайды, PDF с таблицами, документы с правилами. Даты бывают в разных формах: «через 2 недели после офис-часов», «до 23:59 в пятницу». Формат не фиксирован, поэтому классический парсер не сработает.
Нужно понимание, а не поиск по ключевым словам. Требуется отличить «обязательное требование» от «пожелания», понять, к какой задаче относится дедлайн, и связать задание с лекциями, которые нужны для его выполнения.
Нужен агент, а не один запрос. Что делать с файлом, зависит от его содержимого. Это лекция, и тогда достаточно конспекта. Это задание, и тогда нужны требования, дедлайн и поиск нужных лекций в этом же предмете. Решение принимает модель в цикле с инструментами, как в лекции 04 (run() с tools).
3. Пользовательский сценарий (его же показываем в демо)
Пользователь открывает приложение и видит вкладки предметов. Создаёт предмет «LLM-Agents».
Загружает PDF. Для MVP только PDF.
Агент обрабатывает файл и показывает карточку:
конспект (ключевые идеи, термины, 5–10 пунктов);
тип документа (лекция, задание, правила курса);
дедлайны и требования, если они есть, у каждого пометка «страница N» и цитата-источник;
связанные материалы: «для этого задания пригодятся лекции 01 и 04».
На вкладке «Календарь» собраны все дедлайны по всем предметам. Есть кнопка «Экспорт в .ics».
Если дата не указана («объявим в чате»), агент не выдумывает её, а ставит статус «дата не определена» и подсказывает указать вручную.
4. Что входит в MVP, а что остаётся на финал
MVP (первый контроль)	Финал
Вкладки предметов, загрузка PDF	Другие форматы: DOCX, PPTX, ссылки
Конспект по каждому файлу	Вопросы по материалам предмета (RAG)
Извлечение дедлайнов и требований со ссылкой на страницу	Автосвязывание «задание → нужные лекции» на большом корпусе
Календарь внутри приложения и экспорт .ics	Синхронизация с Google Calendar
Запуск через docker compose up	Деплой на сервер по ссылке (+2 балла)
Правило для презентации: лучше маленький MVP, который реально работает вживую, чем широкий, который падает. Ко всему, что не вошло в MVP, у нас должна быть готова фраза «это в планах на финал, потому что…».
5. Агент: из чего он состоит (лекция 04)
Модель. Любой OpenAI-совместимый провайдер. Ключ, BASE_URL и MODEL_NAME лежат в .env, как в слайдах.
Инструменты (@tool):
read_pdf(file_id, pages) читает текст постранично;
list_materials(subject) показывает, что уже загружено в предмет;
save_summary(file_id, ...) сохраняет конспект;
save_deadline(subject, title, due_date, requirements, source_page) сохраняет дедлайн;
link_materials(task_id, file_ids) связывает задание с лекциями.
Цикл: модель сама решает, какие инструменты вызвать и в каком порядке, и останавливается, когда файл обработан.
Структурированный вывод (лекция 03, constrained decoding): дедлайны приходят строго по JSON-схеме (title, due_date или null, requirements[], source_page). Это надёжнее, чем парсить текст постфактум.
Текущая дата и часовой пояс передаются в системный промпт, иначе «в следующую пятницу» посчитать нельзя.
6. Архитектура (достаточно простой, чтобы её можно было защитить)
Бэкенд: FastAPI (или Streamlit, если важнее скорость разработки), SQLite для предметов, файлов, конспектов и дедлайнов.
Фронт: вкладки предметов, список файлов, карточка файла, календарь.
Агент: отдельный модуль agent/ с инструментами, промптами и схемами.
Docker: Dockerfile, docker-compose.yml, .env.example с API_KEY, BASE_URL, MODEL_NAME.

MVP (4 балла):
Запуск вживую (1). Подготовьте 2–3 демо-файла и прогоните их заранее. Живое демо лучше делать на реальных материалах курса, это убедительно.
Чистый репозиторий (1). Дата создания не раньше сентября 2026. Нужны Dockerfile, .env.example, README с командой запуска, ФИО и GitHub-ники всех четверых, раздел «Какой LLM и зачем». Без мусора и мёртвого кода.
Ядро с LLM (2). Это конспект и извлечение дедлайнов, работающие на новом файле, который вы не показывали заранее.
Технические вопросы (2 балла, индивидуально). Каждый должен уметь объяснить: зачем нужен каждый файл репозитория, почему выбраны именно эти решения и от чего отказались. На презентации должен выступить каждый, хотя бы на одном слайде.
8. Заготовки ответов «почему так, а не иначе»
Почему не RAG в MVP? Файл обрабатывается целиком или постранично, этого достаточно. RAG нужен для вопросов по всему предмету, а это финал. Лекция 03 называет цену «вставить весь документ» (prefill и KV-кэш), поэтому длинные файлы режем по страницам.
Почему структурированный вывод? Дедлайн нельзя пропустить из-за сломанного формата.
Почему .ics, а не Google Calendar? Не нужен OAuth, и это работает у всех календарей. API откладываем на финал.
Почему API, а не свой vLLM? Лекция 03 советует API на этом курсе: нет инфраструктуры, а объём маленький.
Как снижаем стоимость? Стабильный системный промпт (префикс-кэш), max_tokens, небольшая модель для конспектов.
Борьба с галлюцинациями: у каждого дедлайна есть источник (страница и цитата), дата null вместо выдумки, пользователь может отредактировать результат.
9. Риски
Лекционные PDF часто не содержат дедлайнов, и «пустой» результат надо красиво обработать.
Сканы без текстового слоя: в MVP честно пишем «поддерживаем текстовые PDF».
Относительные даты без явной точки отсчёта: помечаем как «требует подтверждения».

StudyHub
Агент-ассистент для учебных материалов. Загружаете PDF в карточку предмета, а агент на основе LLM делает конспект каждого файла, находит дедлайны и требования к домашним заданиям и связывает задания с нужными лекциями. Все дедлайны собираются в календарь с экспортом в .ics.
Проект выполнен в рамках курса «LLM-Agents» (НИУ ВШЭ).
Какую проблему решает
Материалы по предмету разбросаны по десятку файлов. Дедлайны и требования спрятаны в середине слайдов или в описании проекта, а часть дат вообще объявляется в чате. Перед каждой домашкой приходится заново перечитывать документы и вспоминать, какие лекции для неё нужны.
StudyHub собирает всё это в одном месте:
вкладки по предметам и загрузка PDF;
конспект по каждому файлу (ключевые идеи и термины);
дедлайны и требования с указанием страницы и цитаты-источника;
связь «задание → нужные лекции» внутри предмета;
календарь дедлайнов и экспорт в .ics.
Если даты в документе нет, агент не выдумывает её: дедлайн получает статус «дата не определена», и пользователь может указать дату вручную.
Быстрый старт (Docker)
Нужны установленные Docker и Docker Compose.
Склонируйте репозиторий:
git clone https://github.com/<org>/studyhub.git
cd studyhub
Создайте файл с настройками и впишите свои значения:
cp .env.example .env
Переменные описаны в разделе «Переменные окружения».
Запустите:
docker compose up --build
Откройте http://localhost:8000.
Данные (база SQLite и загруженные PDF) хранятся в каталоге data/, он подключён к контейнеру как том и не попадает в git.
Остановить приложение: docker compose down.
Переменные окружения
Переменная	Описание	Пример
API_KEY	Ключ API провайдера LLM	sk-...
BASE_URL	Адрес OpenAI-совместимого API	https://api.openai.com/v1
MODEL_NAME	Название модели	gpt-4o-mini
DATA_DIR	Каталог для базы и файлов	./data
Файл .env с реальными значениями не коммитится. В репозитории лежит только .env.example с плейсхолдерами.
Какой LLM используется и зачем
Провайдер: <провайдер> через OpenAI-совместимый API (клиент openai и BASE_URL из .env).
Модель: <название модели>.
Что делает модель. Она работает как агент в цикле с инструментами и сама решает, что делать с файлом:
читает PDF постранично (read_pdf);
определяет тип документа: лекция, задание, правила или другое (set_doc_type);
пишет конспект и выделяет ключевые термины (save_summary);
извлекает дедлайны и требования в структурированном виде: название, дата или null, список требований, страница и цитата (save_deadline);
для заданий смотрит список материалов предмета (list_materials) и связывает задание с нужными лекциями (link_materials).
Зачем здесь LLM. Документы неструктурированные: даты записаны как «через две недели после офис-часов» или «объявим в чате», обязательные требования перемешаны с пожеланиями, а связь задания с лекциями нигде не указана явно. Регулярные выражения и поиск по ключевым словам с этим не справятся, нужно понимание текста.
Как мы снижаем риск ошибок. Ответ приходит по JSON-схеме и валидируется (при невалидном ответе одна повторная попытка). У каждого дедлайна есть страница и цитата. В системный промпт передаются текущая дата и часовой пояс, поэтому относительные даты считаются корректно. Неоднозначные даты помечаются «требует подтверждения».
Почему так, а не иначе.
Без RAG: файл обрабатывается постранично целиком, для конспекта и дедлайнов этого достаточно. RAG понадобится для вопросов по всему предмету.
Без агентного фреймворка: цикл с инструментами написан вручную (около 30 строк) и понятен целиком.
API вместо собственного сервера: у проекта маленький объём запросов, поэтому содержать собственную инфраструктуру (vLLM) не нужно.
Ограничения MVP
Поддерживаются только PDF с текстовым слоем. Сканы без распознанного текста отклоняются с понятным сообщением.
Календарь работает внутри приложения и через экспорт .ics. Синхронизации с Google Calendar пока нет.
